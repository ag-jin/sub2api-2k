## 门禁 C 实测：输入/输出是否被裁切（与 204 同夹具 A/B）

夹具（**专属命名，已清理**）：分组 `zz-probe-claude-205`(id 13)、账号 `zz-probe-mock-205`(id 21，
`type=apikey`、`base_url=http://127.0.0.1:19099`、假令牌)、key `zz-probe-key-205`(id 32)；

| 观测项 | 204（升级前） | 205（升级后） |

| `/v1/messages` 上游收到消息数 | 41/41 | 41/41 |

### 结论一：输入没有被裁切

41 条进 → 41 条出，两条入口、两个版本都一致；最旧标记 `M-OLDEST-TURN-01` 在出站体里。
代码层原因：`applyAnthropicCompatFullReplayGuard`（12 条滑窗）只作用于
`ForwardAsAnthropic` 的 Responses 分支，而 codebuddy 在
`shouldForwardOpenAIResponsesViaRawChatCompletions` 处**提前 return** 到 CC 直转路径，根本不经过该守卫。

### 结论二：输出没有被裁切

mock 回放 40 片 × 50 字符，客户端实收：

| 路径 | 收到 |
| --- | --- |
| CC 非流式 | `finish_reason=stop`，2000 字符，40 片 |
| `/v1/messages` 非流式 | `stop_reason=end_turn`，2000 字符，40 片 |
| `/v1/messages` 流式 | **40 个 `text_delta` 事件**，`stop_reason=end_turn` |

### 结论三：「失忆」的真实机制不是长度，是**内容被改写**

同一份请求，出站体里用户消息被净化器改写（204/205 均如此，205 起 `/v1/messages` 也如此）：

- `cc_rollout_flag=on;` → **整段删除**（用户正文里的内容凭空消失）
- `build_number=11128` → `build_number=11-128`
- system 身份句被改写、`x-anthropic-billing-header` 段被剥离

这是仍未修的全角色净化问题（参考实现 `codebuddy2api/core/system_identity.py::filter_system_identity`
只动 system/developer）。**本版把净化管线接到了 Claude 协议入口，因此该改写现在覆盖两条入口。**

### 结论四：输出侧的真实风险是「思考吃光预算」，不是网关截断

mock 模拟上游只回 `reasoning_content` 且 `finish_reason=length`（buddy 真实失败形态）：

- CC 非流式：`finish_reason=length`，`content=0`，usage `completion_tokens=7`
- `/v1/messages` 非流式：`stop_reason=max_tokens`，空 text 块
- `/v1/messages` 流式：thinking_delta 正常下发，`message_delta.stop_reason=max_tokens`

网关**如实转发**了「零正文 + 预算耗尽」，没有也不该替上游补内容。
既有护栏是 `codeBuddyThinkingMinBudget=8192`：客户端 `max_tokens < 8192` 时强制关思考，
给正文留出空间；预算很大时上游思考无自身上限，可能把预算吃光。

### 附带发现（未修，记录在案）

- **非流式响应丢 thinking**：`aggregateCodeBuddyCCResponse` 只拼接 `delta.content`，
  不回传 `reasoning_content`，故非流式 `/v1/messages` 只得到一个空 text 块而不是 thinking 块；
  流式正常。属既有缺口（本版未引入，也未修）。
- **`parallel_tool_calls`**：`/v1/messages` 出站体仍带该字段（Anthropic→Chat 桥所加），
  CodeBuddy 官方客户端不发；上游对非预期字段敏感（同 `tool_choice`），但尚无实测证据。

### 夹具踩坑（供下次参考）

假令牌账号会被 `codebuddy_keepalive/checkin/growth` 调度器（每分钟）碰到真实
`www.codebuddy.cn` → 账号被标 `temp_unschedulable` → 调度 `pool=0` → 客户端 **503**。
**必须在同一窗口内「先清临时不可调度、立刻发流量」**，不能分两次跑。

## 生产事故与修复（502）

### 现象与根因

用户 14:05 把 `/opt/sub2api-copy/sub2api` 替换为 v0.1.205 制品（sha `7bd9f334…`，**与 dev 同一制品**），
随后正式站 502。实测 `sub2api-copy` 处于 `activating`、`ExecMainStatus=1`、**重启计数 1551**，18080 端口无监听：

```
Failed to initialize application: apply migration 226_add_usage_log_effective_model_indexes_notx.sql
  (non-tx statement 1): pq: must be owner of table usage_logs
```

根因**不是** v0.1.205 的代码：生产库由 SQL dump 以 `postgres` 角色恢复，public schema
105 张表**全部归 `postgres`**，而服务以应用角色连库；上游 v0.2.x 起迁移改为**启动必跑**，
迁移里的 `COMMENT`/`ALTER` 需要对象归属权 → 启动即失败。这正是
`deploy/CARD_DB_UPGRADE.md` 记录并给出方案 A 的已知问题。

关键差别：**dev 装了 preflight drop-in，生产没有**。dev 的
`/etc/systemd/system/sub2api-dev.service.d/card-db-migrate-preflight.conf` 从 v0.1.193 起就在，
生产的 drop-in 目录里只有 `v0.1.180-card.conf`，`/opt/sub2api-copy/` 下连
`card-db-migrate-preflight.sh` 都没有。所以 dev 门禁全绿**并不能**证明生产能起来——
dev 的迁移是 pre-start 以 postgres 身份补跑的，生产从来没人装这一步。

生产还压着 **22 个待应用迁移**（`226` + `227`–`239` 共 22 个，本地 `comm` 实测），
即 192 → 205 的累积差。

### 处置（方案 A，文档指定路径）

1. **备份**：`/opt/sub2api-copy/backups/pre-205-20260930T140800Z/`
   —— `sub2api-pre205.dump`（65 MB，`pg_dump -Fc` 全库）+ `sub2api-schema-pre205.sql`（373 KB）。
   （踩坑：目录先由 root 建，`sudo -u postgres pg_dump` 写不进去 → `chown postgres` 后重跑。）
2. **装 preflight**：从 205 制品取 `deploy/card-db-migrate-preflight.sh` 与
   `deploy/systemd/card-db-migrate-preflight.conf`，用 base64 传输保证逐字节一致，
   落地 sha 与制品相同（脚本 `d6af857b…`、conf `27ebfcf5…`）。
   conf 默认就指向生产路径（`CARD_BIN=/opt/sub2api-copy/sub2api`、`CARD_DB=sub2api`），无需改。
3. **手工先跑一次 pre-step**（便于单独排查，不进 systemd 流程）：
   `sh /opt/sub2api-copy/card-db-migrate-preflight.sh` → `Database migrations completed`，退出 0，
   `schema_migrations` **280 → 302**（恰好 +22）。
4. `systemctl daemon-reload && systemctl restart sub2api-copy`。
